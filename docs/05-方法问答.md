# 05 方法问答（三层追问）

> 规则：每题先给 20 秒版本，再准备一句"如果要展开，我可以讲……"。**答不上来的，回去补实验，不是背表述。**

## 第一层：这项目是干什么的

**Q1 一句话介绍**
> "一个 RAG 检索策略的评测台：用 200 条 408 真题当评测集，测 chunk 大小、overlap、embedding、rerank 对召回和延迟的影响，产出可复现的对比表。"

**Q2 为什么不做知识库问答产品**
> "产品形态谁都能搭，评测才是分水岭。我要回答的是'参数怎么选'，不是'能不能跑'。"

## 第二层：方法是否站得住

**Q3 chunk 怎么切的？边界规则是什么？**
> 自己写的滑窗：按段落聚合到接近 size，超出则在最近的句号/换行处切，不跨标题；overlap 从上一块尾部取固定字符。**不用 LangChain 的 splitter，因为它的递归分隔符顺序在我的语料上会把公式切碎。**

**Q4 为什么 512 不是最优？**
> 数据说话：在 X 语料上，256/64 的 recall@5 比 512/0 高 Z 个点，因为 408 题答案通常集中在 1–2 段、单段 200–400 字，512 的块把两个不相关段落粘在一起，稀释了 BM25 的 term 权重。

**Q5 标注可靠吗？gold 谁标的？**
> 我自己标，规则是"只给这一段能不能答题"；隔天重标 20 条抽检，一致率 8x%；错标会直接抬高或压低 recall，所以我把它当作系统误差来源之一写进限制。

**Q6 只有 200 条够吗？**
> 够做配置间的相对比较（配对设计，同题同 gold），不够做绝对性能声明。所以我只报"相对提升 + CI"，不报"达到 SOTA"。

**Q7 延迟怎么测的？**
> warmup 3 次，测 30 次，报 P95 而不是均值——均值会被个别慢请求掩盖。

**Q8 为什么用 recall 不用 precision？**
> 检索阶段下游是 LLM，多给几条不致命，漏掉才致命；所以召回优先，再用 rerank 控精度和延迟。

## 第三层：边界、失败、反思

**Q9 结果不显著怎么办？**
> 我已经准备了分层分析：按题型、按 query 长度切。如果各配置差别 <2 个点，我会改结论为"chunk 不是瓶颈"，并给出证据（例如 dense 在短 query 上退化）。

**Q10 rerank 值不值？**
> 数据：recall +A 点，P95 从 X ms 到 Y ms。在交互式场景（要求 <500ms）不值；在离线批处理场景值。这就是帕累托图的意义——没有绝对值，只有取舍。

**Q11 如果重做，你会改什么？**
> 三件事：① query 集扩到 500 条并做双人标注；② 加混合检索（BM25+dense RRF），它通常比单一检索稳；③ 把"是否跨章节"作为协变量做分层，而不是事后分析。

**Q12 你的数据和别人有什么不同？**
> 领域特定：术语密集、答案集中、query 短。通用 benchmark（如 MTEB 的检索任务）不覆盖这种分布，所以我要自建。

**Q13 成本多少？**
> 全本地方案 0 元（bge-small + BM25，CPU 可跑）；API 方案约 X 元/200 题 × 28 组，因为 embedding 做了磁盘缓存，只算一次。

**Q14 为什么不用现成的 RAG 框架？**
> 框架把切分和检索都封装了，我恰恰要测这两步；用框架会让我说不清"到底是我的参数起作用还是它的默认值起作用"。

**Q15 这个项目和 408 有什么关系？**
> 评测集是 408 真题，语料是操作系统教材。它同时是我的复习工具——我能看到"哪些知识点我的知识库根本检索不到"，那些就是我复习的盲区。
