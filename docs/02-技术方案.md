# 02 技术方案

## 1. 架构

```
408 真题 ──► query 集（200 条，人工标 gold 段落）
                │
教材/笔记 ──► 切分器 ──► chunk 集 ──► 索引 ──► 检索 top-k ──► 指标
              (size,overlap)        BM25 / dense         recall@k
                                                          MRR@10
                                                          nDCG@10
                                                          P95 latency
                                                          cost
```

**关键点：gold 标在"段落"上，不标在 chunk 上。** 因为 chunk 大小是自变量，如果 gold 跟着 chunk 走，实验就循环论证了。判定规则：检索到的 chunk 若覆盖 gold 段落的中点，算命中。

## 2. 自变量（网格）

| 变量 | 取值 | 说明 |
|---|---|---|
| chunk_size | 128 / 256 / 512 / 1024（字符） | 中文按字符近似 token；1 token ≈ 1.5 汉字，512 字符 ≈ 340 token |
| overlap | 0 / 64 | 相对 size 的 12.5%–25% 是常见区间 |
| retriever | bm25 / bge-small / bge-m3 | 至少 2 个才算"对比" |
| rerank | off / bge-reranker-base | 只对 top-20 重排，再取 top-5 |

## 3. 因变量（指标）

- **recall@k** = 命中的 gold 段落数 / 该题 gold 段落总数，对 query 取平均。k=5 为主。
- **MRR@10** = 第一个命中位置的倒数的平均。
- **nDCG@10**：二值相关性（命中=1），用于对"命中在第几位"更敏感。
- **P95 延迟**：单次 query 的端到端耗时（含检索 + rerank，不含生成），warmup 3 次后测 30 次取 P95。
- **成本**：若用 API，按 token 计价，折算"每题每次查询成本（元）"。

## 4. 控制变量（写进 README，否则结论不可信）

1. 同一份语料、同一份 query、同一台机器。
2. 同一分词方式（BM25 用字符 bigram，中文不分词也能打）。
3. 随机种子固定；dense 检索若用 HNSW，ef 固定。
4. 延迟测量关掉其他大程序；每配置重复 3 次取中位数。
5. 报告时**同时给均值和 CI**。

## 5. 统计方法

- **配对 bootstrap**：对 200 条 query 的逐题得分做有放回重采样 1000 次，得到 (最优 − 默认) 差值的 95% CI。CI 不含 0 才能说"显著"。
- 可选加分：多配置比较用 **Friedman 检验 + Nemenyi 事后检验**（scikit-posthocs 一行）。
- 不要用 t 检验硬套（recall 是比例，不是正态）。

## 6. 代码结构

| 文件 | 职责 | 依赖 |
|---|---|---|

| `src/bm25.py` | 字符 bigram 的 BM25 | 无 |
| `src/metrics.py` | recall@k / MRR / nDCG | 无 |
| `src/eval.py` | 单配置评测，输出 CSV | 无 |
| `src/run_grid.py` | 网格循环 | 无 |

## 7. 扩展点（有余力再做，别一开始就做）

- **混合检索**：BM25 + dense 分数加权（RRF），通常比单一检索强，是一个容易出彩的对比。
- **查询改写**：把口语 query 改写成术语 query，看 recall 变化。
- **分块语义化**：按标题/段落切 vs 定长切，验证"语义切分是否真的更好"。
