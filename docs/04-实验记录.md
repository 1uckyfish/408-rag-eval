## 2026-11-07 W1 基线：BM25 + 18 篇语料 + 120 条 query

配置：
- corpus: os-01..os-18（18 篇、32 927 字、166 段）
- queries: 120 条（q001–q120，2009–2021 真题改写；gold 全部标完：1 段 94 条、2 段 24 条、3 段 2 条）
- retriever=bm25（字符 bigram），top_k=5

结果：recall@5 = 0.9306，MRR@5 = 0.7925，nDCG@5 = 0.8006，P95 = 0.45 ms（75 chunks）

观察（重要，决定 W2 怎么做）：
1. **recall@5 随 size 单调上升，到 1024 已经 0.975 —— 这是语料太小造成的天花板，不是 BM25 真的强**。1024 时全库只有 39 个 chunk，top-5 相当于取回全库 13%，几乎必然覆盖 gold 段。
2. 因此 size 越大越"好看"这件事没有决策价值；要比就得在**同一 k 下比 chunk 数与召回的成本**（recall vs 平均 chunk 数），或者固定 chunk 数上限再比。
3. overlap=64 在 512 上小幅有帮助（0.9306→0.95），在 128 上反而有害（0.7097→0.6861），在 1024 上无影响 —— "overlap 越大越好"不成立，得按 size 分别看。
4. 延迟全部 < 2.5 ms，BM25 在这个规模上完全不是瓶颈；P95 随 chunk 数线性增长（278 chunks→1.18ms，39 chunks→0.32ms）。
5. 语料是"按 408 大纲自撰摘要"，很多段落与真题答案近乎逐字对应（os-12 p8 / os-14 p9 / os-08 p6 与三条 query 几乎同句），所以召回偏高、且 BM25 的字符 bigram 在这批 query 上特别占便宜（query 保留了术语原词）。

下一步：
- dense 单点（同 size=512，bge-small-zh）做 Q2 对照；同一 k 下比，别只比 chunk 数；
- 图 1 画 recall 与 chunk 数的双轴，把"越大越好"的假象讲清楚；
- 语料若继续扩（目标 512 时 ~200 chunks），复跑本表。


## 2026-11-08 语料扩张 18 → 36 篇（把天花板压下来）

配置：
- corpus: os-01..os-36（36 篇、67 814 字、306 段），新增 18 篇全部是"算例变体 / 易错辨析 / 多步推导"，与旧段无近似重复（check_corpus 的 13-gram Jaccard 检测，0 对 ≥0.5）
- queries: 120 条、gold 全部不变（新篇是新文件，旧段序号未动，所以**不需要重标**）
- retriever/top_k 不变

扩张前后对照（同 size、同 k）：

| size | chunk 数（前→后） | recall@5（前→后） | recall@1（前→后） |
|---|---|---|---|
| 128 | 278 → 591 | 0.7097 → 0.5653 | 0.3542 → 0.3042 |
| 256 | 144 → 303 | 0.8556 → 0.7403 | 0.5403 → 0.4736 |
| 512 | 75 → 160 | 0.9306 → 0.8403 | 0.6264 → 0.5264 |
| 1024 | 39 → 89 | 0.9750 → 0.9250 | 0.6681 → 0.5028 |

观察：
1. **天花板确实被压下来了**：512 从 0.9306 降到 0.8403（−9pt），1024 从 0.975 降到 0.925（−5pt），recall@1 全线下降 5–17pt。降幅与 chunk 数增长同向，说明之前的"高分"里有相当一部分纯粹来自库小。
2. **但没压干净**：1024 仍有 0.925（89 chunks）。要让 1024 也有区分度，语料得再翻一倍（~70 篇），边际收益已经不高，先停在这里。
3. **overlap 的方向反转了**：512 上 overlap=64 现在 +3.9pt（0.8403→0.8792），128 上 +3.6pt；而扩语料前 128 上是 −2.4pt。说明 overlap 的作用不是单调的，它取决于 chunk 是否刚好切断答案段——这正好是需要用网格去测的东西，不能先验假设。
4. 但 120 条 query 上 1 条 ≈ 0.83pt，**3–4pt 的差异只相当于 4–5 条题，不能写成"显著"**；答辩被问就答"方向一致但样本量不足以做显著性检验"。
5. G1 门槛（0.3–0.8）在 512 上仍略超（0.8403）。语料规模限制要写进 limitations：自撰语料 36 篇、共 6.8 万字，约为真实 408 教材的 1/5。

下一步：
- dense 单点（bge-small-zh，512/0）做 Q2；
- 若要继续压天花板：再补 20–30 篇（优先 I/O 与文件系统，这两块题最少）；
- 图 1 用扩张后的数据重画，并在 README 里放"扩张前/后"对照，把"发现测量饱和 → 修语料 → 指标回落"讲成方法学故事。


## 2026-11-08 Q2：dense 单点（bge-small-zh-v1.5）vs BM25

配置：
- 同一批语料（36 篇 / 306 段）、同一批 120 条 query、同一套 gold、同一个 k=5
- dense 用 `BAAI/bge-small-zh-v1.5`（512 维，CPU 编码），余弦相似度，`src/dense_eval.py`
- 延迟口径：BM25 是"分词+打分"，dense 是"单条 query 编码+相似度排序"，都含各自的检索前处理

| 配置 | recall@5 | MRR | nDCG | P95(ms) |
|---|---|---|---|---|
| BM25 512/0 | **0.8403** | **0.6830** | **0.6970** | **1.51** |
| dense 512/0 | 0.7600 | 0.5590 | 0.5840 | 15.89 |
| BM25 256/0 | **0.7403** | **0.6120** | **0.6230** | **2.24** |
| dense 256/0 | 0.6780 | 0.4890 | 0.5120 | 14.84 |

观察：
1. **小模型 dense 全面输给 BM25**：512 上 recall 差 8.0pt（0.8403 vs 0.7600），256 上差 6.2pt；MRR/nDCG 差距更大（12pt / 11pt），说明 dense 不仅"该找到的没找到"，而且"找到了也排得靠后"。
2. **延迟差一个数量级**：BM25 P95 1.5ms，dense 15.9ms（CPU，含单条 query 编码）。也就是说 dense 慢 10 倍、还更不准。
3. 原因不是"向量检索不行"，而是**场景不匹配**：query 是 408 术语密集的短句（"页表项 2B、页大小 2^10B 时页目录最少多少项"），字符 bigram 恰好能吃到"页表/页目录/2B"这些术语的重合；bge-small 只有 24M 参数，对长尾术语的语义区分不如字面匹配。语料又是自撰摘要、术语与 query 同源，进一步放大了 BM25 的优势。
4. dense 的 512 仍然优于 256（0.760 vs 0.678），趋势与 BM25 一致 —— size 越大越好这个结论在两个检索器上都成立。

**Q2 的结论（一句话）**：在这个语料和 query 形态下，BM25 与 dense 的取舍没有悬念 —— 又慢又差，不换。真正值得换的是"当 query 变成口语化长句、术语被同义改写时"，而那需要用改写版 query 再测一轮才能证明。

## 2026-11-09 recall@1 的拐点：recall@5 会骗人

`recall@5` 随 size 单调上升（0.565 → 0.925），看上去"越大越好"。但把 k 降到 1，趋势在 512 掉头：

| size | overlap=0 r@1 | overlap=64 r@1 | overlap=0 r@5 | overlap=64 r@5 |
|---|---|---|---|---|
| 128 | 0.3042 | 0.3958 | 0.5653 | 0.6014 |
| 256 | 0.4736 | 0.4819 | 0.7403 | 0.7389 |
| 512 | **0.5264** | **0.5292** | 0.8403 | 0.8792 |
| 1024 | 0.5028 | 0.4903 | 0.9250 | 0.9292 |

观察：
1. **r@5 单调升、r@1 在 512 见顶**（0.5264 / 0.5292，1024 掉到 0.5028 / 0.4903）。机制：size 越大 chunk 越少、越容易"盖住"gold 段，所以 r@5 涨；但 1024 字的 chunk 往往横跨两三个考点，排序第一名被"邻居考点"抢走，r@1 反而掉。
2. **两个指标给相反的推荐**：只看 r@5 会选 1024，只看 r@1 会选 512。真实系统里 top-5 是给读者看的，但 top-1 常常直接喂给下游（或决定用户是否再点），所以取舍要看"下游消费几个结果"。
3. 数据文件 `results/grid_recall_k.csv`（8 行，含 r@1/r@3/r@5），由 `py -3 src\plot_recall1.py` 现算并出图。
4. 答辩可用的说法：**"我记得 r@5 是单调的，所以特意算了 r@1，发现在 512 拐头——这就是我不建议把 1024 当默认配置的原因。"** 这比只报一个数更能说明你懂指标。

## 2026-11-10 标注一致性抽检：40% 的严格一致，但结论没翻

做法：随机 20 条（分层抽样，概念 9 / 计算 7 / 综合 4，种子 20261109）在**不给原始答案**的条件下重标一遍，与首标比对。工具 `src/make_consistency_sample.py`（抽样藏答案）、`src/show_paras.py`（查段号）、`src/check_consistency.py`（对比）。

**先说清这轮的效力**：首标由 4 个子代理借助 BM25 top-5 候选完成；本轮重标由一个**独立的子代理**在没有候选、也没有答案的条件下完成。所以这测的是"**流程可复现性 + 候选提示的影响**"，不是"人工一致性"——对外不能声称是 human agreement。

| 指标 | 值 |
|---|---|
| 完全一致（段落集合相同） | **8/20 = 40%** |
| 有重叠（至少一段相同） | 10/20 = 50% |
| 平均 Jaccard | 0.433 |

12 条不一致里，**8 条是"两个都对的段之间换了选择"**（q003 死锁策略 vs 同类资源公式、q052 检测矩阵 vs 避免矩阵、q062 死锁检测 vs 资源分配图、q063 置换算法段、q074 簇分配、q080 二级页表 vs 多级页表推导、q091 用户级/内核级线程、q116 特权指令 vs 系统调用），4 条是真分歧（q031/q043/q059/q050，其中 q050 重标判定"语料缺批量消费方案"，首标硬标了有界缓冲的两段）。

**关键：换成重标的 gold 后，指标动多少？**（同一批 20 条，512/0）

| gold 版本 | recall@5 | MRR | nDCG |
|---|---|---|---|
| 首标（现有，候选提示下标的） | 0.850 | 0.608 | 0.662 |
| 独立重标 | 0.825 | 0.592 | 0.628 |
| 两者取并集（任一段算命中） | **0.867** | **0.775** | **0.740** |

观察：
1. **recall@5 只掉 2.5pt（≈0.5 条题）**，说明"512/0 = 0.84、1024/64 = 0.93"这类结论对 gold 的具体选段不敏感——这是可以对外讲的稳健性证据。
2. **MRR/nDCG 对 gold 选择敏感得多**：并集口径下 MRR 从 0.608 跳到 0.775（+16.7pt）。机制很直白：单段 gold 时，如果模型把"另一个同样正确的段"排第一，排序分算 0。**所以 MRR 只能当参考，硬结论要用 recall@k。**
3. 严格一致率 40% 不是"标得差"，而是"同一道题常有多段都能答"——这本身就是评测数据的固有歧义，把单段 gold 当唯一真值会系统性低估排序质量。

讲述口径：**"我做过一致性抽检：20 条隔天独立重标，严格一致 40%、有重叠 50%。但我没有停在这个数字上——我把两版 gold 都拿去跑，recall@5 只差 2.5 个点，说明主结论稳；MRR 差 17 个点，说明排序类指标受标注歧义影响大，所以我对外只讲 recall@5。"**

局限（必须主动说）：本轮重标者是模型不是人，"人工一致率"仍缺；要补的话是同一份 `round1.md` 由**你本人**再标一遍，跑同一个脚本。

## Q3：rerank 单点 —— 结果是负的（2026-11-11）

### 配置

- 召回：BM25 512/0，取 top-20（160 chunks）
- 重排：`BAAI/bge-reranker-base`（cross-encoder，512 token 截断）
- 取前 5；**与"同一批 20 条候选不重排"比较**，避免把召回差异算到排序头上
- 120 条 query 全量，单机 CPU

### 结果

| 指标 | BM25 基线 | +rerank | 差值 |
|---|---|---|---|
| recall@1 | 0.5264 | 0.4806 | **−4.58pt** |
| recall@5 | 0.8403 | 0.8139 | **−2.64pt** |
| MRR | 0.6829 | 0.6494 | **−3.35pt** |
| nDCG@5 | 0.6971 | 0.6592 | **−3.79pt** |
| P95 延迟 | 2.69 ms | **3 988 ms** | ×1483 |

逐题：recall@5 涨 8 / 跌 14 / 平 98；recall@1 涨 14 条（有局部改善，但被更多下跌抵消）。

### 结论

**在这个语料上，通用 cross-encoder rerank 是负收益，而且代价是 1.5 秒。** 
基线已经 0.8403，重排反而把 14 条从"找得到"推成"找不到"——说明 reranker 的判断与本任务的"哪个段落能答这道题"并不一致。

### 三个可能的解释（未验证，如实写在文档里）

1. **打分单元与标注单元错位**：gold 标的是段落，送进去的是 512 字 chunk（常跨 2–3 段）。chunk 里有一段相关、一段无关时，cross-encoder 给整块打一个分，信息被平均掉了。
2. **领域不匹配**：bge-reranker-base 是通用检索对训练的；本语料是教材式密集术语，query 又是短术语串，reranker 更看重语义近似而不是"这条能不能回答问题"。
3. **截断**：512 token 对 512 汉字 chunk 会截尾，尾部段落直接没被看到。
