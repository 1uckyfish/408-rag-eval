# 失败案例（第⑨步）

默认配置 **BM25 / size=512 / overlap=0 / k=5**，120 条 query 跑完的分布：

| 类别 | 判据 | 条数 | 占比 |
|---|---|---|---|
| A 完全没找到 | recall@5 = 0 | 16 | 13.3% |
| B 找到但排不到第一 | recall@5 = 1 且 recall@1 = 0 | 37 | 30.8% |
| C 多段 gold 只命中一部分 | 0 < recall@5 < 1 | 4 | 3.3% |
| 完全正确 | recall@1 = 1 | 63 | 52.5% |

**最重要的一个数不是 16，是 37。** 召回@5 已经 0.840，但 recall@1 只有 0.526 —— 一半以上的"损失"发生在排序，不在检索。这也是 Q3（rerank）值得做的直接证据。

复现：`py -3 src\find_failures.py`（明细写 `results/failures_512_0.csv`，`--qid q005` 看单条 top-5）。

---

## 1. q005 同词不同义：「索引」

- **query**：文件物理结构中，哪种结构既适合随机访问又便于文件扩展？
- **gold**：`os-12/3`（索引分配，物理结构）
- **top-1**：`os-11/2`（索引文件，逻辑结构），得分 28.94 对 gold 段的 0 命中
- **为什么**：两个段落都反复出现"索引表、按关键字随机存取、占用空间"。BM25 只看字面，"索引"在两种语境里是同一个 bigram，无法区分"逻辑结构里的索引文件"和"物理结构里的索引分配"。
- **能不能修**：query 侧不可修（用户就是会这么问）；语料侧可以写一句对照辨析，或在 query 里补"盘块/索引块"这类区分性词。

## 2. q008 符号噪声：P1/P2/P3 撞上银行家算例

- **query**：三个进程 P1、P2、P3 互斥使用 N 个单元的缓冲区，P1 放入正整数、P2 取奇数、P3 取偶数，如何用信号量实现同步与互斥？
- **gold**：`os-05/5` + `os-05/6`（PV 模板 + 环形缓冲完整代码）
- **top-1**：`os-06/4`（银行家算法），74.36 分，gold 段 0 命中
- **为什么**：语料里的银行家算法、死锁检测算例大量出现 `P1、P2、P3`、`资源`、`分配`。这些编号被当成了内容词，把一条同步题硬拉到死锁章节。
- **能不能修**：能，且便宜 —— 把 `P\d+`、`进程\d` 这类编号从 query 和索引里一起归一化（或当停用词）。**这是本项目最值得做的一处工程修正**，预计能把 A 类再压掉几条。

## 3. q001 语料缺细节：并行与并发的四组关系

- **query**：单处理机系统中，进程之间、处理机与设备、处理机与通道、设备与设备之间，哪些活动是并行、哪些只是并发？
- **gold**：`os-01/2`（并发 vs 并行定义）
- **top-1**：`os-01/0`（操作系统定义），同文档相邻段
- **为什么**：语料只写了"并行需要多处理机、单处理机只能并发"这个总原则，**没有逐条回答"进程与进程、处理机与设备、处理机与通道、设备与设备"这四种组合**。gold 标的是"最接近的段"，不是"能完整回答的段"。
- **能不能修**：要补语料（os-01 加一段四组关系的对照）。**这类是语料覆盖缺口，不是检索算法问题**，写报告时要和"检索失败"分开算。

## 4. q026 术语同族混淆：read 系统调用 vs 内存映射

- **query**：进程用 read 系统调用读取磁盘文件时，若数据不在内存会怎样、是否进入核心态、参数是否需要文件名？
- **gold**：`os-15/7`（一次读操作的完整处理过程）
- **top-1**：`os-10/0`（内存映射文件），41.99 分
- **为什么**：内存映射那段写着"不再调用读、写系统调用"，字面上包含"读、写、系统调用"，与 query 高度重合，但讲的是相反的机制。语料里"read/读/系统调用"这三个词散落在 I/O 软件层、I/O 请求、文件系统三章。
- **能不能修**：query 侧可加"磁盘 I/O 请求的完整流程"这类限定词；语料侧把 `read` 的调用链集中到一段（现在 `os-15/7` 是唯一一段，太单薄）。

## 5. q016 题目参数不在语料 + 同主题算例竞争

- **query**：页大小 1KB，4 个页框装入时刻 130、230、200、260、访问位均为 1，地址 17CAH 的页号及 FIFO 与 CLOCK 下物理地址是多少？
- **gold**：`os-09/4`（FIFO/Belady）+ `os-09/5`（CLOCK/改进 CLOCK）
- **top-1**：`os-28/5`（改进型 CLOCK 扫描细节），58.15 分
- **为什么**：`130、230、200、260、17CAH` 这些数字在语料里当然不存在（语料是通用讲解）。检索只能靠"FIFO、CLOCK、页框"这几个词，而 os-28 专门写了一个更细的 CLOCK 算例，把这些词全占了。同时 512 的切分把 os-09/4 和 os-09/5 切进不同的块。
- **能不能修**：这是**计算类 query 的固有困难**——具体参数不进索引。可行的缓解是"算法名 + 关键概念"加权，或做 query 里的数值剥离。

## 6. q009 多段 gold 只命中一段：EAT 与 LRU 分处两章

- **query**：页大小 4KB、TLB 10ns、内存 100ns、缺页 10^8 ns、驻留集 2 页时，一次访存的平均时间是多少？
- **gold**：`os-09/5`（LRU/CLOCK）+ `os-09/9`（EAT 公式）
- **命中**：`os-09/8` 排名第 1（覆盖其中一段），另一段没进 top-5 → recall@5 = 0.5
- **为什么**：公式在 os-09/9、淘汰规则在 os-09/5，两段必须合起来才能算。**这暴露的是 gold 多段标注的代价**：只要漏一段，指标就只给 0.5 分，哪怕检索给的前 5 条里其实有完整答案的另一半。
- **能不能修**：不能完全修，但报告里要写明"多段 gold 共 26 条，它们的 recall 上限天然低于单段题"。

## 对外怎么讲这三类

- **A 类（16 条）**：检索失败，主因是同词不同义、符号噪声、语料缺口。可修的是符号噪声，其余属语料/表达问题。
- **B 类（37 条）**：检索成功但排序失败 —— 这是 rerank 的靶子，也是 Q3 的立项依据。
- **C 类（4 条）**：多段标注的结构性代价，不是算法问题。

一句话版本：**"我的失败案例里，超过一半不是找不到，是找到了没排第一。"** 这句话比任何一条具体案例都更能说明下一步该做什么。

## 附：符号噪声消融实验（把案例 2 的猜想验掉）

只看一条 q008 就说"编号是噪声"是不严谨的。做了个最小消融：**只在 query 侧**把 `P1/P2/p1…` 和 `进程1/进程2` 剥掉（语料不动），重跑 BM25 512/0。

- 被改写的 query：5 条（q008、q027、q084、q095、q105）
- 命令：`py -3 src\ablation_idnoise.py`

| 版本 | r@1 | r@5 | MRR | nDCG |
|---|---|---|---|---|
| baseline | 0.5264 | 0.8403 | 0.6829 | 0.6971 |
| 去编号 | 0.5306 | 0.8486 | 0.6913 | 0.7054 |
| Δ | +0.0042 | +0.0083 | +0.0083 | +0.0083 |

**结论要说得诚实**：只影响 5 条题，翻了 1 条（120 条里 1 条 = 0.83pt）。方向对、幅度小 —— 符号噪声真实存在，但**不是主要矛盾**；主要矛盾仍是 37 条 B 类（排不到第一）。这条实验的价值是"我把猜想去验了"，不是"我发现了大问题"。
