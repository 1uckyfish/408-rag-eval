# 00 选题与定位

## 1. 为什么是 C（RAG 评测），不是 B（shell + 测量）

两个方案的差别不在难度，在**能不能被追问三层**。

| 维度 | B（shell+测量） | C（RAG 评测） |
|---|---|---|
| 上手门槛 | 低 | 中（环境 + 领域知识） |
| 8 周做完概率 | 95% | 70% |
| 金钱成本 | 0 | 0–200 元 |
| 稀缺性 | 低 | 高 |
| 与 408 协同 | 强 | 弱 |
| 与 AI 导师相关性 | 弱 | 强 |
| 被追问三层后 | 靠测量章节 | 靠实验设计和统计 |
| 最大风险 | 同质化，被当成复刻 | 结果不显著 / 被当成调包 |

**共同点**：救赎都在"测量"。B 测的是内核行为，C 测的是检索质量。真正决定答辩表现的不是选题，是**有没有留下自己产生的数据**。

选 C 的代价要认：要花两周折腾环境、结论可能不显著、还要花点 API 钱。换来的是稀缺性和与 AI 方向的相关性。

## 2. 答辩叙事（记熟，30 秒讲完）

> "我备考 408，发现市面上的 RAG demo 都在讲'我搭了个知识库问答'，但没人回答'chunk 该切多大'。
> 我就把 408 历年真题当评测集，把操作系统教材切成知识库，做了 chunk × overlap × embedding × rerank 的网格实验，200 条题、**28 组配置**、每组跑 3 次。
> 结论是：默认的 512/0 在这个场景下不是最优，optimum 是 X，recall@5 提升 Z 个点，延迟只涨 W ms；
> 另外 rerank 在 5 条返回的场景下不划算——它把 recall 提升了 A，但 P95 延迟翻了 B 倍。
> 代码和一个 CSV 都在 GitHub 上，你可以自己跑。"

这段话里每一句都可以被追问，所以每一句都有对应的实验（见 docs/05）。

## 3. 三种结局的预案（现在就写好，别到时候慌）

### 结局 A：网格出现明显最优（理想）
- 交付：热力图 + 帕累托 + 结论句。
- 强化：补统计检验（配对 bootstrap CI），说"差异显著，p<0.05"。

### 结局 B：各配置差别很小（很常见）
不要硬编故事。改讲：
- "在这类**短查询 + 术语密集**的语料上，chunk 大小的影响被 BM25 的精确匹配掩盖了"——然后给证据：按题型（选择/大题）、按 query 长度分组看差异。
- 这反而是更成熟的结论：**"chunk 大小不是瓶颈，rerank 才是"**。很多论文也是这么说的。

### 结局 C：环境/预算失败
- 全本地化：bge-small-zh（~100MB）+ BM25，0 元。
- 若连模型都下不动：只做 BM25 的 chunk 网格，仍是一个完整项目（只是叙事弱一档）。

## 4. 不要做的事

- ❌ 不要做成"聊天界面 + 知识库"的 demo（那就是被当成复刻的典型）。
- ❌ 不要用 LangChain 的 `RecursiveCharacterTextSplitter` 当核心卖点（老师会问"它的边界规则是什么"，答不上就穿帮）。切分自己写，20 行。
- ❌ 不要只报平均值。要报 **P95 延迟**、要报 **CI**、要报 **失败案例**。
- ❌ 不要堆 20 个 embedding 模型。3 个足够，深度 > 广度。
